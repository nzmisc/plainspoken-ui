# Working on plainspoken-ui

A React component library distributed as a [shadcn registry](https://ui.shadcn.com/docs/registry), with a Next.js
docs site (components, demos, customizer) and a Storybook. There is no npm package: people copy components into their
apps with the shadcn CLI. Read this before changing anything; it is the contract every file here follows.

## Layout

| Path | What |
|---|---|
| `registry/plainspoken/ui/*.tsx` | Components (`registry:ui`), one file each, kebab-case. Installed to `components/ui/`. |
| `registry/plainspoken/lib/*.ts` | `controls.ts` (height scale), `icons.ts` (icon data), shared non-UI code. Installed to `lib/`. |
| `registry/plainspoken/hooks/*.ts` | Hooks. Installed to `hooks/`. |
| `registry/plainspoken/blocks/<demo>/…` | Bigger pieces built from components, mostly per demo (`mail/message-list.tsx`). Installed to `components/blocks/…`. |
| `registry/plainspoken/examples/*.tsx` | Docs examples, one default export each. Not installed. |
| `registry/items/<name>.json` | One registry item each: what it is and which files it has. **The registry's source of truth.** |
| `registry.json`, `registry/__index__.ts`, `registry/__examples__.ts`, `public/r/` | Generated by `scripts/build-registry.ts`. Never edit by hand. |
| `app/(site)/…` | The docs site: home, `/docs`, `/docs/components/[name]`, `/customize`, `/demos` index. |
| `app/(demos)/demos/<demo>/…` | The demo apps, full-page, each with its own layout. |
| `components/site/` | Site-only components (docs chrome). Built from registry components where possible. |
| `lib/` | Site and build code: `theme.ts` (theme model), `foundation.ts`, `site.ts`, `docs-nav.ts`, `demos.ts`. |
| `stories/` | Storybook stories, mirroring the docs: `foundations/`, `components/`, `blocks/`, `demos/`. |
| `content/` | Demo data that is too big for a TS file (texts, catalogues). |
| `docs/concepts/` | Design notes: what is wanted, open, later, set aside. |

## Commands

- `npm run dev`: the site on :3000 (also regenerates the registry index).
- `npm run storybook`: Storybook on 127.0.0.1:6106.
- `node scripts/build-registry.ts --index`: after adding or changing `registry/items/*.json` or examples (fast).
- `node scripts/build-registry.ts`: also writes `public/r/*.json` (the build does this).
- `node scripts/build-theme.ts`: after changing `lib/theme.ts` or `lib/foundation.ts` (writes `app/theme.css`).
- `npm run icons -- <lucide-name>…`: copy more Lucide icons into `lib/icons.ts`. Names are Lucide's current ones
  (some were renamed: `filter` is `funnel`, `music` is `eighth-note`, `trash-2` is gone, use `trash`).
- `npx tsc --noEmit` and `npx eslint <paths>`: must pass for what you touched.

## The look

Plain HTML, made consistent. When unsure, ask "what would a well-made page from 2005 do, with today's accessibility?"

- **No corner radius anywhere.** Never `rounded-*`. (Avatars too: square.)
- **No shadows** except on floating layers (menus, popovers, dialogs, toasts), and there only `shadow-md` or lighter.
  Borders separate things.
- **Borders**: `border-border` for structure (tables, panels, dividers), `border-input` for the edges of controls.
- **Links in running text** are real links: `text-link underline visited:text-link-visited`. Navigation links
  (sidebars, tabs, menus) are not blue: they use `text-foreground` with a bold or underlined current item.
- **Colours** are only theme tokens: `bg-background text-foreground bg-muted text-muted-foreground bg-secondary
  bg-accent bg-primary text-primary-foreground text-destructive text-success text-warning border-border border-input
  outline-ring text-link`. Never raw palette colours (`text-gray-500`, `bg-blue-600`) or hex, except the chart tokens
  `chart-1`…`chart-5` for data. `muted` is a background; muted text is `text-muted-foreground`.
- **Type**: Geist via `font-sans`, Geist Mono via `font-mono`. Body text 14px. Small print 12–13px. Headings bold, not
  huge. Numbers in tables: `tabular-nums`, right-aligned; their headers stay left-aligned.
- **Density**: tight but not cramped. Table rows about 24–28px. No big empty cards.
- **Dark mode** comes from the tokens; never write `dark:` variants for colours the tokens already handle.
- **Icons**: only from `@/registry/plainspoken/lib/icons`, drawn with `<Icon>` or passed to a component's `icon` prop.
  Never inline SVGs or emoji as icons. Icon-only buttons are `<IconButton label="…">`.

## Components: rules

1. **One height scale.** Interactive controls are exactly `xs 20 / sm 24 / md 28 / lg 36px` tall, border included,
   via the CSS variables from `lib/controls.ts`: `h-(--ctl-h) px-(--ctl-px) text-(length:--ctl-text) gap-(--ctl-gap)
   [&_svg]:size-(--ctl-icon)`, or `CONTROL_BOX`. A `size?: ControlSize` prop adds `controlSize(size)`; leaving it
   out inherits from the nearest `ctl-*` class (md at the root). Don't use React context for sizes. Prove alignment
   in a story with `<Measure>` (`stories/support/measure.tsx`).
2. **Native first.** `<dialog>` for modals and drawers, the Popover API or a small positioning helper for floating
   things, `<details>` for disclosure, native inputs and selects. No Radix, Base UI, React Aria, Headless UI, cmdk,
   date libraries or icon packages. **Do not add npm dependencies.** If something truly needs one, stop and say so in
   your report instead.
3. **Accessible**: follow the ARIA Authoring Practices pattern for the widget (keyboard, roles, focus). Every control
   reachable and operable by keyboard, visible focus (`FOCUS_RING`), labels on everything, `aria-live` for things
   that change on their own. Respect `prefers-reduced-motion`.
4. **Server-component friendly**: no `"use client"` unless the file uses state, effects, context, refs or event
   handlers it defines. A component that only takes `onClick` as a prop does not need it.
5. **API style**: function components, props interface exported as `<Name>Props`, extend the native element's props
   where there is one, `className` merged last with `cn()` from `@/lib/utils`, React 19 `ref` as a plain prop,
   `data-slot="<name>"` on the root. Controlled and uncontrolled where it makes sense (`value`/`defaultValue`/
   `onChange`). Doc comment on every exported component saying what it is for and anything non-obvious, in plain
   sentences. Comments explain why, not what.
6. **Imports inside `registry/`** are only `@/registry/plainspoken/…`, `@/lib/utils`, `react`, `react-dom` and
   (blocks and demo pages only) `next/*`. The build rejects anything else. Import components from their own files,
   not barrels.
7. **Names**: shadcn's where a shadcn component is the same thing (`dialog`, `tabs`, `badge`, `tooltip`, `popover`,
   `dropdown-menu`, `alert`, `accordion`, `avatar`, `card`, `separator`, `skeleton`, `slider`, `progress`, `table`,
   `pagination`, `breadcrumb`, `sidebar`, `kbd`, `calendar`, `date-picker`, `combobox`, `command`, `toast`), and
   plain descriptive names otherwise. Variants: `default | primary | secondary | outline | destructive | ghost | link`
   for buttons; status components use `default | info | success | warning | destructive`.

## Registry items

Every installable thing has `registry/items/<name>.json`:

```json
{
  "name": "tabs",
  "type": "registry:ui",
  "title": "Tabs",
  "description": "One sentence: what it is and what is special about it.",
  "category": "Navigation",
  "files": ["ui/tabs.tsx"],
  "examples": ["tabs-demo", "tabs-variants"]
}
```

- `category` is one of: Controls, Forms, Feedback, Overlays, Navigation, Data display, Layout, Typography, Charts,
  Foundations. Blocks use `"type": "registry:block"` and the demo's name as category (`"Mail"`).
- Dependencies are worked out from imports; list only extras. A file may belong to one item only.
- `examples`: the first is the overview shown at the top of the docs page; the rest get their own sections, titled
  from the file name (`tabs-variants` → "Variants") with the doc comment above `export default` as the description.
  Examples are small, realistic, and use real-sounding content (not "Lorem ipsum", not "Item 1").
- Then run `node scripts/build-registry.ts --index`. The docs page `/docs/components/<name>` appears by itself.

## Stories

- File: `stories/components/<name>.stories.tsx` (blocks: `stories/blocks/<demo>/…`, demos: `stories/demos/…`).
- Title: **`Components/<category>/<title>`**, exactly the item's category and title (the docs link to
  `components-<category>-<title>--docs`). Blocks: `Blocks/<Demo>/<Title>`. Demos: `Demos/<Demo>`.
- Cover: a Playground with args where the props are simple, every variant, every size (with `<Measure>` for
  controls), states (disabled, loading, empty, error, long text), keyboard behaviour described in the doc comment,
  and dark mode needs nothing special. Import from `@storybook/nextjs-vite`.

## Next.js 16 here

`cacheComponents` and `partialPrefetching` are on. In practice:

- Pages are server components. Read data with synchronous `fs` or in a function with `"use cache"` +
  `cacheLife("max")`. No `Date.now()`, `Math.random()` or `new Date()` while rendering on the server.
- A page with `[params]`: `generateStaticParams` for every value, and put the part that awaits `params` inside
  `<Suspense>` (see `app/(site)/docs/components/[name]/page.tsx`). Use `PageProps<"/route/[param]">` for the props.
- Client components that call `useSearchParams()` must sit inside `<Suspense>`.
- `next/link` for internal links in the site and demos. Metadata via `export const metadata` / `generateMetadata`
  (titles, descriptions) on every page: the site is for search engines too.
- Read `node_modules/next/dist/docs/` before using an API you haven't seen here.

## Checking your work

- The dev site (`npm run dev`) and Storybook (`npm run storybook`) show changes live. Look at what you built:
  screenshots via headless Chrome are fine (`google-chrome --headless=new --screenshot=… --window-size=…`).
- Check light and dark, a phone width (375px) and a wide one, and keyboard use.
- `npx tsc --noEmit` and `npx eslint` on your files, and the registry build, before you finish.
- Don't run `next build` while others are working in this checkout (it shares `.next` with the dev server).
